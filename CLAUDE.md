# Claude Instructions

## Project Overview

A clickable, front-end-only prototype of the Permitopolis City Clerk's event permitting site. An
applicant describes an event in a five-step wizard and gets a tier (Instant, Reviewed or Special
event), the permits it needs and a board of to-do cards. The City Clerk, Public Works & Safety and
Health & Legal each see every case's state, whose move it is, and the active permits. There is no
backend: all state lives in one Zustand store in the browser, seeded with 38 cases on a fixed demo
date, Mon, May 3, 2027.

**Key Features:**
- Public landing page for the Clerk's Office (`/`) and a presenter's demo guide (`/demo`)
- Applicant: wizard (`/apply`), my events and to-do board (`/events`), quote, permit with QR code
- City roles: My queue, Cases pipeline, Case detail with "Who's up", Active permits, role tools
- One role switcher, persona picker and Demo menu (reset, demo date, scenario jumps); no login

**Sources of truth:** `docs/spec/prd.md` (the PRD), `docs/spec/flows.md` (flows and decision tree),
`docs/spec/scenarios.json` (demo scenarios), `docs/rime-and-ink-design-system.md` (visual style) and
`docs/plans/2026-10-12-permitopolis-prototype.md` (the build plan; its section 3 says which source
wins where they disagree).

## Build rules for agents

These apply to every change, whoever makes it.

**Stack.** Next.js 16.4 (App Router, Cache Components on), React 19, TypeScript, Tailwind CSS v4,
shadcn/ui on Radix, Zustand, date-fns, Vitest, pnpm. This is not the Next.js in your training data:
read the relevant page in `node_modules/next/dist/docs/` before using an API you are not sure of.

**Pages.** Every `page.tsx` is a thin server component that renders one `'use client'` screen inside
`<Suspense>`. The screen reads the URL with `useParams()` and `useSearchParams()` and reads state
from the store. Do not make `page.tsx` async, do not read `params` or `searchParams` props, and do
not remove the `<Suspense>` in `app/layout.tsx`; the build fails without these boundaries.

```tsx
// app/city/cases/[id]/page.tsx
import { Suspense } from "react";
import { CaseDetailScreen } from "@/components/case/CaseDetailScreen";

export default function Page() {
  return (
    <Suspense fallback={null}>
      <CaseDetailScreen />
    </Suspense>
  );
}
```

**State.** One `EventCase` per event (`lib/types.ts`). Rules are pure functions in `lib/rules`;
every change to a case goes through `transition()` in `lib/state`, dispatched with
`useDemo().dispatch(caseId, action)`. Components never re-implement a rule or mutate a case. Pure
view-models for a screen go in `lib/view/<surface>.ts` with tests.

**Frozen contracts.** `lib/types.ts`, `lib/rules/types.ts`, `lib/rules/config.ts`,
`lib/state/actions.ts`, `lib/state/types.ts`, `lib/routes.ts`, `lib/format.ts`, `lib/dates.ts`,
`lib/data/{inventory,streets,calendar,fees}.ts` and `styles/tokens.css` are shared by every
workstream. Do not edit them from a workstream; report the change you need instead.

**Time and randomness.** The demo runs on a fixed date. Never call `new Date()` with no arguments,
`Date.now()`, `Math.random()` or `crypto.randomUUID()`; lint rejects them. Use `demoToday()` and the
helpers in `lib/dates.ts` (never `new Date('2027-05-03')`, which parses as UTC). Ids are derived
from the case id: `${caseId}:${catalogId}`.

**Copy.** Plain language. Dates read "Sat, Jun 26, 2027" and money reads "$1,240": always use
`lib/format.ts`. Party and tier names come from the label maps in `lib/types.ts`.

**Style.** Rime & Ink tokens only. Use the utilities generated by `styles/tokens.css`
(`bg-surface-1`, `text-fg-secondary`, `border-line-subtle`, `shadow-card`, `rounded-panel`,
`ease-frost`); a test rejects raw hex, `rgb()` and `oklch()` values in `app/` and `components/`.
Indigo is the only action color. Body copy is `text-fg-secondary`; labels and metadata are
`text-fg-label`; `text-fg-tertiary` is for placeholders and decoration only (it fails AA). Party and
tier color always comes with an icon and a label. Backdrop blur is for chrome (top bar, sidebar,
sheets, dialogs), not for repeated rows and cards.

**Dialogs and storage.** No `window.confirm`, `alert` or `prompt`; use the Dialog component. No
direct `localStorage`; go through `lib/state/storage.ts`.

**Imports between surfaces.** A surface imports from `lib/`, `components/ui`, `components/domain`,
`components/map`, `components/calendar` and `components/shell` only, never from another surface's
folder. Surfaces hand off through `lib/routes.ts` and store actions.

**Screens.** City screens work from 1280 px wide; applicant screens and the landing page work down
to 375 px. Keyboard reachable, visible focus, status changes announced with `aria-live`.

**Working in a worktree (parallel builders).**
- Run `pnpm install --frozen-lockfile --prefer-offline` first; a fresh worktree has no `node_modules`.
- Stay inside the paths your brief gives you. Add no dependency; report it if you need one.
- Do not edit `docs/log.md`, `docs/readme.md`, `CLAUDE.md` or the plan. Return your log entry in
  your result; the integrator writes them. This overrides the logging workflow below for builders.
- Before you finish: `pnpm typecheck`, `pnpm lint` and `pnpm test` must pass, then commit your work
  on your branch.

## Plans

**Every plan gets saved to `docs/plans/`, no exceptions.** Whenever Claude makes a plan (in plan
mode, via a planning skill, or when laying out a multi-step approach before implementing), write it
to `docs/plans/` as a Markdown file **before** starting the work, including a plan that was only
presented in chat or approved through plan mode's exit prompt.

- **Filename:** start with the date in `YYYY-MM-DD` format, followed by a descriptive name (e.g.,
  `docs/plans/2026-03-27-auth-system.md`, `docs/plans/2026-03-27-cms-migration.md`).
- **Keep it current:** the plan file is a living document. Whenever the plan changes (the user
  revises scope, an approach is dropped, steps are added, reordered or completed, or implementation
  reveals something that changes the design), update the same file in the same turn. Don't start a
  new file for a revision of the same plan; mark finished steps done and note significant changes
  and why in a short "Changes" section at the bottom.
- **One source of truth:** if the plan-mode plan file lives elsewhere (e.g. `~/.claude/plans/`),
  copy it into `docs/plans/` and keep the `docs/plans/` copy updated from then on.

This keeps plans versioned, reviewable, and accessible across sessions.

## Verification

**Visual/UI verification is the user's job — don't do it.** Do not start a
preview/dev server, drive a browser, or take screenshots to check how something
looks. The user runs their own dev server and verifies the UI themselves.
Functional/logic verification you *should* still do (type-check, lint, build,
and exercising behavior via `curl`/scripts against the running server is fine).
When a change is visually observable, finish your logic checks and hand it to
the user to look at rather than asking which browser to use.

## Logging Requirements

**CRITICAL:** For every code change or feature addition:

1. **Write a log entry** describing what was changed and why
2. **Save to `docs/log.md`** in the following format:

### Log Entry Format

```markdown
## [YYYY-MM-DD] - [Brief Change Title]

**What Changed:**
- Specific file(s) modified or created
- Description of the change

**Why:**
- Reason for the change (feature request, bug fix, refactor, etc.)

**Files Modified:**
- `path/to/file.ext`
- `path/to/file.ext`

---
```

### Example

```markdown
## 2026-03-27 - Added Parent Name field to notification form

**What Changed:**
- Added "Parent Name" input field to the email notification modal
- Updated `submitNotify()` to collect and send parent name to Google Apps Script

**Why:**
- Parents want to be identified when registering interest, not just by email

**Files Modified:**
- `index.html` - Added input field and updated form submission logic

---
```

### When to Log

Log entries are needed for:
- ✅ New features
- ✅ Bug fixes
- ✅ File modifications
- ✅ New file creation
- ✅ Schema/structure changes (e.g., adding columns to Google Sheet)

Don't log:
- ❌ Reading files to understand context
- ❌ Running tests/verification
- ❌ Responding to questions without code changes



### Workflow

1. **Make the code change(s)**
2. **Write the log entry** in the format above
3. **Append to `docs/log.md`**
4. **Inform the user** of what was done in your response
